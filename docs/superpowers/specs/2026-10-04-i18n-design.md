# Internationalization (i18n) design

Status: approved in brainstorming, 2026-10-04. First additional language: Hungarian (`hu`).

## Goal

Make Jev Arena a multi-language application in which a single global language setting switches both the user interface and the datasets that new runs use, while the arena behaves exactly as before. Other people must be able to add their language with documented steps and tooling. English results, frozen evidence and published assets must remain valid.

## Decisions

| Topic | Decision |
|---|---|
| Translatable text scope | UI and report text only. Long docs (`docs/*.md`), long prose in `docs/evidence/*.json` and the Guide's long prose stay English, with an "English only" note. |
| Language setting | One global setting, stored server-side. It drives the UI language and the datasets used by new runs. Every run still records its language. |
| Test data | Each suite slot is wired per language to a **native** dataset of the same task type where one exists, otherwise to a **translated** pack produced by our pipeline, otherwise marked **missing**. |
| Answer labels | Localized labels (e.g. "Számlázás"), mapped to stable ids in `provenance.label_ids`. Scoring code is unchanged. |
| Translation engines | Pluggable: `manual` (export/import), `opus-mt` (offline default), `deepl` and `google` (official free tiers, key in `.env`). Unofficial Google Translate scrapers are not used. |
| i18n library | i18next + react-i18next with JSON catalogs, shared with the Python report exporters. |

## Locale bundle

Each language is one directory:

```
locales/<lang>/
  locale.json     # {code, name, nativeName, status: "complete"|"beta", review, intl: {...}}
  ui.json         # UI strings, namespaced by screen
  report.json     # report-only strings (exporters, ABCD template, README/METHOD-NOTES)
  prompts.yaml    # repo-authored test text: Fresh templates, episode prompts, importer and ABCD prompts
  datasets.yaml   # slot -> native | translated | missing, with licence and label_map
```

`en` is the source of truth. Missing keys fall back to `en` at runtime; `i18n check` reports them.

## 1. Language setting and UI

### Global setting
- Stored in `.arena/settings.json` as `{"language": "en"}` (default `en`).
- `GET /api/i18n` returns `{language, locales: [{code, name, nativeName, status, completeness}]}` built from each `locale.json` plus catalog completeness.
- `POST /api/i18n {"language": "hu"}` validates against available locales and saves the setting (POST because the local token/origin middleware and the UI `api()` helper treat POST as the mutation verb). A run in progress keeps the language it started with; the setting only affects new runs.

### Frontend
- `apps/web/src/i18n.ts` initializes i18next with all bundled catalogs (imported at build time so the app and the standalone report work offline) and `fallbackLng: "en"`.
- Keys are namespaced by screen: `overview.*`, `results.*`, `explore.*`, `operations.*`, `setup.*`, `guide.*`, `abcd.*`, `shell.*`, `errors.*`, `packs.*`, `common.*`.
- Extraction covers `main.tsx`, `Operations.tsx`, `Explore.tsx`, `ABCDCases.tsx`, `Guide.tsx` (headings, labels and table headers only), `ViewHistory.tsx` and `apps/shared/AppShell.tsx` (about 600 strings).
- `navigation.ts` keeps its page ids. `pageNames` becomes a key map and labels are resolved through `t()`.
- The `AppShell` header gets a language switcher that shows `nativeName` and a "beta" tag for beta locales. Switching calls `PUT /api/i18n` and then `i18next.changeLanguage`. `document.documentElement.lang` follows the language.
- Pack and family identifiers ("Arena Fresh", "XNLI", ...) remain identifiers; their display text comes from `packs.<id>` keys.

### Formatting
- `apps/web/src/format.ts` exposes `number`, `percent`, `date` and `duration`, using `Intl` with the active language.
- It replaces every `toLocaleString(undefined, …)`, `toLocaleDateString(undefined, …)`, plain `toLocaleString()` and hand-built `toFixed(…) + "%"` in the UI.
- Plurals use i18next's `Intl.PluralRules` support (`_one`/`_other` suffixes).

### Backend messages
- User-facing errors (about 20, such as suite not prepared, readiness reasons in `controller.py`, and setup/API validation messages) return `{"detail": "<English text>", "code": "<code>", "params": {...}}`.
- The UI shows `t("errors.<code>", params)` and falls back to `detail` when the code is unknown.
- Internal exceptions are unchanged.

## 2. Localized reports

### Full report (`arena/report.py`, `scripts/export_builder_report.py`)
- The standalone report embeds the React bundle, so it reuses `ui.json`.
- The exporter takes `--lang` (default: the global setting), writes `language` into `window.__ARENA_REPORT__` and sets `<html lang>`.
- The report starts in that language, and its switcher works offline across all bundled locales.
- Exporter-added English text (limitations, the README and METHOD-NOTES in the zip) moves to `report.json` keys.

### ABCD report (`scripts/abcd_report_template.html`, `scripts/export_abcd.py`)
- Hard-coded prose (about 60 blocks) becomes `data-i18n="key"` attributes and `t("key", params)` calls in the inline JS.
- `export_abcd.py --lang` injects the chosen `report.json`, merged over `en`, through a new `__I18N__` placeholder.
- A small inline `t()` plus `Intl` formatting replaces `toLocaleString()`. i18next is not loaded in this static file.
- `scripts/abcd_report_data.py` limitation and note strings become keys that are resolved at export time.

### Published assets
- The released files pinned in `results/manifest.json` are not regenerated.
- Localized exports use a language suffix (`…-hu.html`, `…-hu.zip`).

## 3. Language-specific test data

### Slots
A slot is an existing family within a pack:

| Slot id | Pack / family | Task |
|---|---|---|
| `jevbench` | JevBench public | decision tasks |
| `typed-decisions` | Typed decisions | typed decisions |
| `sst2` | Classification / SST-2 | binary sentiment |
| `agnews` | Classification / AG News | topic classification |
| `banking77` | Classification / BANKING77 | intent (banking) |
| `xnli` | Multilingual / XNLI | NLI, 3-way |
| `massive` | Multilingual / MASSIVE | intent (assistant) |
| `scifact` | RAG relevance | retrieval relevance |
| `fresh` | Arena Fresh | executable-policy fixtures |
| `robustness` | Robustness | perturbed Fresh fixtures |
| `episodes` | Warehouse / Tickets workflows | recorded workflows |
| `abcd` | ABCD assessment | support routing and actions |

### `datasets.yaml`
For `en`, every slot is `native` and describes today's sources exactly (pins from `arena/importers.py`). Example `hu` entries:

```yaml
slots:
  sst2:
    source: native
    repo: NYTK/HuSST
    revision: <pinned sha>
    split: validation
    fields: {text: sentence, label: label}
    sample: 500
    drop_labels: [neutral]
    licence: CC-BY-SA-4.0 (GitHub nytud/HuSST; HF card states BSD-2-Clause, so assume share-alike)
    label_map:
      negative: {id: negative, label: negatív}
      positive: {id: positive, label: pozitív}
  banking77:
    source: translated
    from: banking77          # English slot definition supplies cases and labels
    engine: opus-mt
    licence: CC-BY-4.0 (translation of BANKING77)
    label_map: {...}         # 77 stable ids -> Hungarian labels, translated once
  # A slot with no native or translated data yet (format illustration only;
  # every hu slot is mapped in the table below):
  # some-slot:
  #   source: missing
```

### Hungarian mapping

| Slot | Hungarian source |
|---|---|
| `sst2` | native `NYTK/HuSST`, validation split, neutral dropped, 500 sampled |
| `agnews` | native `Davlan/sib200` `hun_Latn`, 7 topics, sample capped at what is available |
| `massive` | native `AmazonScience/massive` `hu-HU` at the existing converted revision |
| `xnli` | native `NYTK/HuCommitmentBank` train+validation (labelled, about 350 items) |
| `banking77`, `scifact`, `jevbench`, `typed-decisions`, `abcd` | translated |
| `fresh`, `robustness`, `episodes` | generated from `locales/hu/prompts.yaml` |

Native sets are different benchmarks. Their results are reported as Hungarian-language results and are not compared one-to-one with English scores.

### Repo-authored text
- `arena/i18n/prompts.py` provides `prompt(lang, key, **params)` backed by `locales/<lang>/prompts.yaml`.
- `fresh.py`, `episodes.py`, `importers.py`, `multilingual.py` and `abcd.py` read every template, question, distractor, injection and legend string through it.
- `locales/en/prompts.yaml` contains the current strings verbatim.
- **Invariant:** English cases generated after the refactor are byte-identical to before. Each English pack's `case_sha256` and `*-manifest.json` sha256 are unchanged. A regression test enforces this using fixtures captured before the refactor.
- Editing `arena/*.py` changes the runtime fingerprint, so runs that are still in progress cannot be resumed across the upgrade. That is already true of any code change. Completed runs and evidence are unaffected.

### Labels
- In a localized case, `question.labels`, `gold`, `acceptable` and `criteria` descriptions are in the target language.
- `provenance.label_ids` maps each localized label to its stable id.
- `contracts.py`, `wire.py`, `scoring.py` and the workers are unchanged.
- Pack builds fail if localized labels within a question are not unique.

### Storage, ids and counts
- Non-English packs are written to `.arena/datasets/<lang>/`. English paths are unchanged.
- Localized case ids carry a language prefix (`hu:classification-sst2-123`), and `Case.language` is set.
- `suites.EXPECTED` and the hard-coded `7671` are derived from `datasets.yaml` per language. English still yields 7671.
- `suite(preset, lang)` and `inventory(lang)` take the language, defaulting to the global setting. Missing slots are listed as unavailable.
- The run manifest records `language`.
- Setup's "Prepare selected" also prepares the active language's packs.

### Licences
- Each pack manifest records the source licence and the engine (for translated packs).
- `THIRD_PARTY.md` gains a per-language section.
- Third-party and translated text stays in ignored `.arena/` and is never committed or redistributed.

## 4. Translation pipeline, tools, docs, testing

### Engines (`arena/i18n/engines.py`)
- Interface: `class Engine: name; def translate(self, texts: list[str], src: str, tgt: str) -> list[str]`.
- Engines register in one `ENGINES` dict.
- **Built in:**
  - `manual`: writes a JSONL of pending texts and reads the translator's file back.
  - `opus-mt`: `Helsinki-NLP/opus-mt-en-<tgt>` at a pinned revision, runs on CPU, optional dependency group `i18n`.
  - `deepl`: uses `DEEPL_API_KEY`.
  - `google`: Cloud Translation v2, uses `GOOGLE_TRANSLATE_API_KEY`.
- Keys stay server-side, are read from `.env`, and are never logged.

### Translation memory
- Stored in `.arena/translations/<lang>/<slot>.jsonl`, one entry per source text: `{src_sha256, src, tgt, engine, model, revision, at, reviewed}`.
- Translation is resumable and never translates the same source text twice.
- A translated pack's manifest records the memory file's sha256, so the pack is frozen once built.
- Only sampled cases and their dependencies are translated: labels and criteria, the SciFact abstracts the sampled cases retrieve, and the ABCD handbook and sampled conversations.
- Labels are translated once into `label_map`, never per case.
- `--dry-run` prints character counts per slot alongside the known free-tier limits.

### CLI (`uv run python -m arena.i18n <command>`)

| Command | Purpose |
|---|---|
| `new-language <code>` | Create `locales/<code>/` from `en` with every slot set to `missing` and `status: beta` |
| `check [--lang L]` | Missing or extra keys, `{{placeholder}}` mismatches, YAML schema validation, duplicate labels, completeness % per file. Exits non-zero on errors. Runs in CI. |
| `extract` | Runs `i18next-parser` to find strings in code that have no catalog key |
| `translate --lang L --slot S [--engine E] [--dry-run]` | Fill the translation memory for a slot |
| `review --lang L --slot S [--sample N]` | Terminal side-by-side review that records `reviewed` approvals |
| `tm export|import --lang L --slot S <file>` | Share a translation memory |
| `prepare --lang L` | Build the language's packs (also triggered from Setup) |

### Docs
- `docs/i18n/CONTRIBUTING-TRANSLATIONS.md`: step-by-step guide to adding a language (catalogs, prompts, dataset slot mapping, finding native datasets and checking licences, translate and review, beta versus complete criteria, running `check`).
- `docs/i18n/ARCHITECTURE.md`: the components in this spec and how data flows through them.
- `docs/i18n/DATASET-SLOTS.md`: what each slot measures and what makes a native substitute acceptable.
- README: a short "Languages" section.

### Hungarian content
- `locales/hu/*` are written in this project and marked `status: beta`, `review: needs native review` until a native speaker signs off.

### Testing
- English cases are byte-identical, checked against hashes captured before the refactor.
- `i18n check` passes for `en` and `hu`.
- `format.ts` gives correct Hungarian number, percent and date output. Plural keys resolve.
- Native pack builders work against small local fixtures without network access.
- Translation-memory resume and freeze work with a fake engine.
- Label-map uniqueness failures are detected.
- Both report types export in `hu`, with `lang` set and no untranslated keys.
- The settings API validates and stores the language. Error codes are translated.
- The existing `pytest`, node tests and `npm run build` stay green.
- Tests that hard-code `LANGS` or `7671` become parametrized by language, with English values unchanged.

## Delivery phases
1. i18n core: locale bundle, settings API, i18next, UI extraction, format helpers, error codes, `check`/`new-language`/`extract`, Hungarian `ui.json`, docs skeleton.
2. Reports: full and ABCD exporters with `--lang`, `report.json` for `en` and `hu`.
3. Data: `prompts.yaml` extraction with the byte-identical invariant, `datasets.yaml`, language-aware suites, native Hungarian packs, translation engines and memory, `translate`/`review`/`tm`/`prepare`, contributor docs completed.

## Out of scope
- Translating `docs/*.md` and evidence prose.
- Right-to-left layout support. It is not needed for `hu`, but `locale.json` reserves `dir` for later.
- Committing or redistributing any third-party or translated dataset text.
- Regenerating the published release assets.
